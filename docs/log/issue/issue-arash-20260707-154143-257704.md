projio injects the indexio chatbot `hooks:` entry into the project's COMMITTED mkdocs.yml, which breaks downstream CI (GitLab Pages) builds.

SYMPTOM (sirocampus): `make build` in CI aborts at mkdocs config load:
`Config value 'hooks': The path '.../.projio/site/indexio_chat_hook.py' isn't an existing file.`
This silently broke the Pages deploy from when the line was added (sirocampus commit 0831c51) until 2026-07-07 — the live site was frozen at an April build for months with no error surfaced to the user.

ROOT CAUSE: With `site.framework: mkdocs` and `site.chatbot.enabled: true`, projio writes
    hooks:
      - .projio/site/indexio_chat_hook.py
into the project's committed `config_file` (per `.projio/config.yml → site.mkdocs.config_file: mkdocs.yml`). But `.projio/site/` is gitignored (`.gitignore` `.projio/site/` and a broad `site/`), so the hook file never exists in a fresh CI checkout and mkdocs aborts. The injected snippet is localhost-only (`http://127.0.0.1:8309/...`), so it must never appear in a public/CI build regardless.

projio ALREADY HAS THE CORRECT MECHANISM: the gitignored overlay `.projio.mkdocs.yml` (referenced by `.projio/servers.json`) also carries the same `hooks:` line and is what `projio site serve` uses for local preview. So the chatbot hook belongs ONLY in that overlay.

FIX: Ensure projio injects the chatbot hook (and any localhost/preview-only hooks) ONLY into the gitignored `.projio.mkdocs.yml` overlay used for local serve — never into the committed `config_file` that downstream CI builds from. Audit the `projio site build`/sync code path that mutates `site.mkdocs.config_file`.

WORKAROUND already applied in sirocampus (commit b2f9cb5, 2026-07-07): manually removed the `hooks:` line from committed mkdocs.yml to unblock Pages. This regresses if projio re-injects on next sync, so the fix must also stop re-adding it to the committed file.

VERIFY: on a clean checkout, `projio site build` / `make build` succeeds with no hooks error; `projio site serve` still injects the chatbot locally via the overlay. Also consider making the snippet CI-safe (relative/configurable URL, no-op when the chat backend is unreachable).
