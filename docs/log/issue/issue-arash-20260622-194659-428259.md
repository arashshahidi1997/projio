# `note_search` MCP tool returns empty — hardcodes `corpus="notes"` which isn't a real corpus in pixecog

## The bug

`mcp__projio__note_search(query="...")` hardcodes `corpus="notes"` in its implementation. But pixecog's `.projio/indexio/config.yaml` defines no corpus named `notes` — only `bib | codelib | docs`. The 974-file `docs` corpus indexes everything under `docs/log/` (handoffs, results, ideas, meetings, tasks), so the content the user wants to search IS indexed — just not under the corpus name `note_search` looks for.

Result: `note_search` returns `results: []` for *every* query in pixecog, regardless of whether the content exists.

## Empirical evidence (pixecog, 2026-06-22)

Three test queries, freshly indexed (20-min full build just completed: docs 6892 chunks, bib 10820, codelib 3192):

| Query | `note_search(...)` result | `rag_query(corpus="docs", ...)` result |
|---|---|---|
| `"spindle TF-burst Dimitrov coupling"` | `results: []` | 6 highly relevant hits (idea SPEC + A1 result + working figs + definitions) |
| `"ripple detection methods comparison sub-05"` | `results: []` | 6 hits across multiple threads (result notes, handoff, TAC coupling deliverable) |
| `"place fields motion quaternion bug cohort yield"` | `results: []` | 6 hits telling the full bug → fix → cohort-rerun story |

So the content is there and retrievable, just not via `note_search`.

## Root cause hypothesis

`note_search` likely hardcodes `corpus="notes"` from when projio used a separate `notes` corpus convention; in pixecog (and probably other projio-managed projects), notio notes live inside `docs/**/*.md` and get indexed under the `docs` corpus instead. The tool's corpus selector hasn't been updated to either (a) accept a `corpus` parameter, (b) auto-detect which corpus actually contains notio frontmatter content, or (c) fall back to `docs`.

## Suggested fixes (in order of preference)

1. **Accept a `corpus` parameter on `note_search`** (default `"notes"` for back-compat, but allow `"docs"`) — minimal change, matches `rag_query`'s signature exactly. Callers in pixecog would pass `corpus="docs"`.
2. **Auto-detect by inspecting the indexio config** — find the corpus whose source `selector` matches `docs/log/**` (or has the most notio frontmatter content) and route there.
3. **Fall back to `docs` when `notes` is missing.**

(1) is the safest behaviour change. (2) is the cleanest semantics. (3) is the cheapest workaround.

## Pixecog workaround documented

A feedback memory was pinned in pixecog ([feedback_rag_query_corpus_docs.md](https://gitlab.lrz.de/sirotalab/pixecog/-/blob/master/memory/feedback_rag_query_corpus_docs.md), `memory/` lives outside the repo at `~/.claude/projects/-storage2-arash-projects-pixecog/memory/`) telling future agents to call `rag_query(corpus="docs", ...)` directly instead of `note_search`. That's a workaround, not a fix.

## Acceptance test for the fix

After fix, in pixecog:
```python
mcp__projio__note_search(query="spindle TF-burst", k=5)
```
should return ≥3 of: the spindle SPEC idea note, the A1 result note, the working-figs README — same hits `rag_query(corpus="docs", query="spindle TF-burst")` already returns.

Source project context: pixecog, branch master, observed 2026-06-22 while building cross-thread retrieval workflow for multi-session agentic work. Multi-session coordination is a core pixecog workflow and `note_search` being silently broken affects every fresh agent session that tries to look up cross-thread context.
