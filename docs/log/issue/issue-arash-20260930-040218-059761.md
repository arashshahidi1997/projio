INFRA BUG (projio notio MCP): `note_create` errors on its response parse — returns `{"error":"Expecting value: line 1 column 1 (char 0)"}` for `result` and (by inference) `handoff` types, regardless of payload (minimal and full both fail). The note is NOT created. Looks like a server-side response-serialization bug, not a payload problem. Workaround in use: write the notio note file directly to `docs/log/<type>/<type>-arash-<ts>.md` (schema-matched) and let `px-build-and-push` reindex. Observed 2026-09-30 in pixecog session. Fix the MCP response serialization so agents don't have to bypass it.

## Related Notes

- [[issue-arash-20260927-015610-712117.md]] — Same notio note_create MCP tool, another opaque-error bug on a different param (frontmatter/YAML vs response parsing)

## Resolution (2026-11-06)

Fixed in projio de52abd + 17d9e22 and notio 83ae4f4. Root cause: `note_create` did a bare `json.loads` on `frontmatter`; agents passed the on-disk YAML form, so the call raised "Expecting value: line 1 column 1 (char 0)" and wrote nothing. Across the pixecog transcripts all 78 failed calls had YAML frontmatter and none failed without it, so this and the "empty response" reports are one bug. `frontmatter` (note_create) and `fields` (note_update) now take a mapping, a JSON object string or YAML; anything else gets an error naming the parameter and the expected form. `note_create` also returns the note `id`. The same fix went into notio's own MCP server. Regression tests in tests/test_mcp_notio.py and packages/notio/tests/test_mcp_fields.py. Checked through the real MCP server in projio and pixecog with YAML frontmatter; `note_search` from pixecog still works (falls back to the docs corpus). Pixecog MCP servers pick it up on restart.
