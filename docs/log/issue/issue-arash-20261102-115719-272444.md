## Resolution 2026-11-10 (projio-pipeio · marimo + preamble)

Fixed in pipeio `bc3fd10`. Root cause of both failures: the MCP server env (uv-tools projio) has no marimo, so `MarimoBackend()` raised on init and was dropped from the backend registry. Marimo notebooks then auto-detected as percent, and `format: marimo` made `get_backend` raise `Unknown notebook format: 'marimo'. Available: percent`. Reproduced on a scratch copy of pixecog's `preprocess_ieeg/investigate_ttl_xcorr_sync` with the old code.

- The marimo backend now always registers. Its command is resolved lazily and falls back to bare `marimo`.
- `pipeio_nb_publish` (request 1): for marimo it runs `marimo export html` into `.build/notebooks/<name>.html` with no ipynb and no sync step. The projio wrapper resolves the project Python (`pixi run python` under pixi) and takes `python_bin` and `timeout`. MyST is refused for marimo, and it warns when `publish_html` is unset.
- `docs_collect` (request 2) indexes that HTML for `publish_html: true` entries. It never executes notebooks.
- `pipeio_nb_snapshot` (request 3) now reaches the marimo path. It reads only a session JSON written by this run, where it used to return stale outputs after a failed export.
- Tests cover both backends (`tests/test_nb_publish_snapshot.py`). One test runs real marimo, and it passes under pixecog's pixi env.

pixecog: once the MCP server is restarted, `pipeio_nb_publish(flow="preprocess_ieeg", name="investigate_ttl_xcorr_sync", format="html")` replaces the manual `pixi run python -m marimo export html`.
