# Feature: `pipeio nb open <flow> <notebook>` — one-command marimo launch (agent-pairing) + tab-completion + dedupe, plus an MCP variant

## Motivation
Launching an exploratory **marimo** notebook for human/agent pairing currently means hand-typing the full path plus a fixed flag bundle, e.g.
`marimo edit --headless --no-token --host 0.0.0.0 code/pipelines/<flow>/notebooks/explore/<nb>.py`.
This is repetitive and error-prone, and duplicate servers on the *same* notebook get orphaned — a stale headless marimo server keeps "owning" the file and can silently save over on-disk edits (this actually happened: a 22h-old headless server on a fixed port shadowed newer edits). A pipeio command that (a) resolves flow+notebook, (b) launches with the agent-discoverable flag bundle, (c) dedupes against already-running servers, and (d) tab-completes both args, removes this friction and makes agent auto-attach one call.

Stopgap already in place (pixecog): a `marimo-pair` pixi task = `marimo edit --headless --no-token --host 0.0.0.0` (no fixed port → marimo auto-picks; append `--port N` to pin). **This pipeio command should become the canonical launcher that the pixi task later delegates to.**

## Reuse existing scaffolding — do NOT rebuild
- **`pipeio nb` argparse subcommand group** (`packages/pipeio/src/pipeio/…`): existing subcommands `pair, sync, diff, exec, publish, status, scan, migrate, lab`. Add `open` beside `lab`. CLI is **argparse** (no click/typer).
- **`nb lab`** already "Build symlink manifest and launch Jupyter Lab" — the launcher precedent; mirror its structure for a marimo launch.
- **`packages/pipeio/src/pipeio/notebook/backend_marimo.py`** — already knows how to invoke marimo (command prefix + version detection + format handling). Reuse its command prefix for the launch instead of hardcoding `marimo`.
- **`nb status` / `nb scan`** already enumerate a flow's notebooks (`explore/` + `demo/`). Reuse that resolution for both the launch target and the completion candidates.

## Command design
`pipeio nb open <flow> <notebook> [--port N] [--demo] [-- <extra marimo args>]`
- Resolve to `code/pipelines/<flow>/notebooks/{explore,demo}/<notebook>.py` — `explore/` by default, `--demo` (or auto-detect if only in `demo/`) for demo. Accept the notebook with or without `.py`. Clear error if flow or notebook is unknown (list candidates).
- Launch (via `backend_marimo` command prefix): `marimo edit --headless --no-token --host 0.0.0.0 [--port N] <resolved path>`.
  - **No fixed port** → marimo auto-picks a free one (`marimo/_server/start.py`: `port = port or find_free_port(DEFAULT_PORT)`), so several notebooks coexist; `--port N` pins.
  - Flag rationale: `--no-token` → the server registers in marimo's local registry so agents/the `marimo-pair` skill auto-discover it; `--host 0.0.0.0` → reachable over SSH; `--headless` → no browser (remote/pairing default). Print the resolved URL on start.
- **Naming:** use `open` — NOT `pair` (`nb pair` already means jupytext format pairing; avoid the collision). A thin top-level alias `pipeio explore <flow> <nb>` → `nb open` is acceptable if desired.

## Dedupe-or-attach
Before launching, read marimo's local server registry; if a server already serves the resolved notebook path, **print/return its existing URL instead of starting a duplicate** (prevents orphaned headless servers silently owning + overwriting the file). Add `--force` to launch anyway.

## Tab-completion (argcomplete)
- Add `argcomplete` dynamic completers: **flow** completer reads the pipeio flow registry (same source as `pipeio flow list`); **notebook** completer, given the partially-parsed flow, lists `code/pipelines/<flow>/notebooks/{explore,demo}/*.py` stems.
- Add the `# PYTHON_ARGCOMPLETE_OK` marker + `argcomplete.autocomplete(parser)` hook; add `argcomplete` as a dependency; document one-time `eval "$(register-python-argcomplete pipeio)"`.

## MCP variant
Expose `pipeio_nb_open(flow, notebook, port=None, demo=False, reuse=True)` via the **projio MCP server** (alongside the existing `pipeio_nb_*` tools — this is why the task is filed at the projio monorepo, not just the pipeio package). Launch detached and return structured `{url, host, port, pid, session_id, notebook_path, reused: bool}` so an agent launches AND attaches in one call (no `discover → ps-match`). Honor dedupe (`reuse=True` → return the existing server if present).

## Acceptance criteria
- `pipeio nb open <flow> <nb>` starts a headless, token-less marimo on an auto-picked free port serving the resolved notebook and prints the URL.
- Re-running for the same notebook prints the existing URL (no duplicate) unless `--force`.
- `--port N` pins the port; unknown flow/notebook gives a clear error listing candidates.
- Tab-completion completes flow names and flow-scoped notebook names.
- `pipeio_nb_open` MCP tool returns the structured dict; a second call with `reuse=True` returns `reused=True` + the same URL.
- Tests (follow pipeio's existing test layout): path resolution (explore/demo, with/without `.py`, bad flow/nb); dedupe logic (mock registry); completion candidate functions.
- Docs: update `pipeio nb` help + the pipeio-guide skill wherever notebook launching is described.

## Cross-references
- Convergence target: pixecog `pixi run marimo-pair` task (`pixi.toml`) and the `marimo-pair` Claude skill (`.claude/skills/marimo-pair/scripts/{discover-servers,execute-code}.sh`) — this command must produce servers those scripts discover (i.e. `--no-token`). After shipping, the pixi task can delegate to `pipeio nb open`.
