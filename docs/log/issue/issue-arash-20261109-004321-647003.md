pipeio_target_paths disagrees with the Snakefile's BidsPaths on where the bids root goes, and doesn't see runtime-added registry families.

Call (pixecog, 2026-11-09): pipeio_target_paths(flow="spectrogram_burst", group="bursts", member="bursts", entities={"subject":"03","session":"24","task":"pre"})
Returned: derivatives/spectrogram_burst/sub-03/ses-24/spectrogram/bursts/ieeg/sub-03_ses-24_task-pre_bursts.tsv
The flow's own Snakefile builds out_paths = BidsPaths(_registry, repo_abs(config["output_dir"]), inputs) and gives:
derivatives/spectrogram_burst/spectrogram/bursts/sub-{subject}/ses-{session}/ieeg/sub-..._bursts.tsv
(registry entry: bids: {root: spectrogram/bursts, datatype: ieeg}). So the tool puts the `root` after sub/ses, BidsPaths before. Using the tool's path, `snakemake -n <path>` failed with MissingRuleException.

Second part: families the Snakefile adds to the registry at runtime (`_registry[f"bursts_{band}"] = {...}` for each band) are unknown to the tool ("Unknown family 'bursts_spindle'").

Expected: target_paths resolves the same path the flow's BidsPaths does (ideally by calling BidsPaths with the same registry), so agents can dry-run explicit targets. Workaround used: build BidsPaths in Python from config.yml.

## Resolution (2026-11-18)

- pipeio `7714b97`, projio `749846e`. Cause: `SimpleResolver` (behind `pipeio_target_paths` and `PipelineContext`) built paths by hand with `bids.root` after `sub-`/`ses-`; `BidsPaths` calls `snakebids.bids()`, which puts root first.
- One shared implementation, `pipeio.bidspath`: `family_kwargs` is the registry merge `BidsPaths.__call__` now runs, and `bids_path` is a snakebids-free copy of `snakebids.bids()` for specs v0_0_0, v0_11_0, v0_15_0 (the MCP env has no snakebids). Parity with snakebids is tested and was checked in pixecog's env. The spec comes from the Snakefile's `set_bids_spec(...)` (pixecog: v0_0_0), base-input wildcards from `pybids_inputs`. `sub`/`ses` and `subject`/`session` both work; open wildcards are returned as `missing_entities`.
- Runtime families: when the group is not in config.yml, the tool loads the Snakefile in the project env (`python_bin`, auto-resolved by projio to `pixi run python`) with `snakebids.generate_inputs` stubbed, so no dataset scan, and uses the registry of the flow's `BidsPaths`. Cached in `.projio/pipeio/cache/registry/<flow>.json` until a flow file changes (projio's managed .gitignore block now ignores that dir). `snakefile=True` lists those families too.
- Checked read-only on pixecog: `bursts/bursts` with subject 03, session 24, task pre gives `derivatives/spectrogram_burst/spectrogram/bursts/sub-03/ses-24/ieeg/sub-03_ses-24_task-pre_bursts.tsv` (exists on disk); `bursts_spindle` and `detect_spindle_ieeg_cortex` resolve through the Snakefile (first call 45 s, then 0.2 s), both exist. A full Snakefile load without the stub took over 5 min on raw/, so no `snakemake -n` was run.
- Tests: pipeio `tests/test_bidspath.py` (layout per spec, snakebids parity, spectrogram_burst-shaped flow, runtime family + cache invalidation, load failure); projio `test_target_paths_passes_snakefile_and_project_python`.
