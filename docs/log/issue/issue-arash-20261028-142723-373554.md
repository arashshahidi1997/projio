[from pixecog] `projio sync` regenerates questio plan pages even when the project has turned questio off

**What happened (pixecog, 2026-10-28):**
- pixecog set `skills: disabled: [questio-*, session-wrap, marimo-session]` in `.projio/config.yml` (using the new switch from issue …105833).
- The planning model moved away from questio: a hypothesis registry plus state docs (pixecog WR-D12).
- Every `projio sync` still prints `[+] questio: regenerated 11 plan docs` and rewrites `docs/plan/{index,questions,milestones,roadmap,evidence}.md`, `docs/plan/mkdocs.yml` and `docs/deliverables/` indexes from `plan/*.yml`.
- `questio_docs_collect` also emits warnings for result notes whose free-text `question:` no longer maps to a questio question. This is now expected: results carry `hypothesis:` instead.

**Expected:** a per-project way to turn a subsystem's sync step off. Turning off its skills alone doesn't stop sync from regenerating its outputs. For example:
- `questio: {enabled: false}`, or
- `sync: {skip: [questio]}` in `.projio/config.yml`.

`projio sync` would then skip the regeneration and say so (`[-] questio: disabled`). Related: the deliverables index generation currently lives inside questio_docs_collect. If that is independent of questio planning, it should run even when questio is off, or move to its own step.

**Context:** pixecog will drop `docs/plan/` when its WR-P1 lands. Until then the regenerated pages are stale noise in every sync.

## Resolution (2026-10-28)

- **Item 1, switch** (`a2099f1`): `questio: {enabled: false}` in `.projio/config.yml`. This follows the existing `<subsystem>: {enabled: ...}` convention rather than `sync: {skip: [...]}`, because the switch has to cover the MCP tool and the mkdocs include as well as sync. When off: sync prints `[-] questio: disabled (config)` and writes nothing under `docs/plan/`; `questio_docs_collect` returns `{"questio": "disabled (config)"}`; sync stops adding the Plan include.
- **Item 2, deliverables** (`1018dce`): the `docs/deliverables/` indexes are their own sync step, independent of questio. It runs where a generated index already exists (or questio's plan exists) and never overwrites a page without the generated marker. The MCP tool still generates them too.
- Item 3: the free-text `question:` warnings are unchanged. With questio off they no longer appear, because nothing is collected.
- Tests: tests/test_questio_switch.py. Docs: configuration reference (`questio`, deliverables, `skills`) and handbook skills page.
- Verified read-only on pixecog: without the key the dry run is unchanged; with the switch simulated in-process it prints `[-] questio: disabled (config)` and still regenerates the deliverables indexes. pixecog sets the key and runs the real sync itself.
