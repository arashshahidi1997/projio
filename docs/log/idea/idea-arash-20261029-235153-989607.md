# [from lit-studio, R49] mcp-config: when merging into an existing .mcp.json, also point other projio.mcp.server entries at the current interpreter

## Problem

The user is moving the MCP setup from conda to pixi/uv. projio itself is now a uv tool (`/storage2/arash/infra/uv-tools/projio/bin/python3`, Python 3.12, editable from this repo), and `projio mcp-config` writes its own `projio` entry with that interpreter. But when it merges into an existing `.mcp.json`, it keeps every other entry as it was. Entries that run projio's own server for another root, e.g. a lab hub (`"args": ["-m", "projio.mcp.server"]`, `PROJIO_ROOT=/storage/share/sirocampus`), keep the old conda interpreter. Regenerating the config therefore never moves them off conda.

## Evidence

- `projio mcp-config --root /storage2/arash/projects/lit-studio` (preview, 2026-10-29) shows:
  - `projio` → `/storage2/arash/infra/uv-tools/projio/bin/python3`;
  - `worklog` → `/home/arash/.local/bin/worklog-mcp`;
  - `sirocampus` → `/storage/share/python/environments/Anaconda3/envs/rag/bin/python` (carried over from the existing file).
- `src/projio/mcp/config_gen.py` `generate_server_defs()` (lines ~33-68) builds only `projio` and `worklog`; `write_mcp_config()` merges the rest unchanged.
- The same conda path is in pixecog's `.mcp.json` (`projio` and `sirocampus` entries).
- Related, not part of this request: `.projio/projio.mk` in sirocampus and pixecog still sets `PROJIO ?= …/Anaconda3/envs/rag/bin/python -m projio` (and NOTIO, MKDOCS, DATALAD on conda).
- **The uv interpreter works for these entries.** lit-studio ran a smoke test on 2026-10-29: `/storage2/arash/infra/uv-tools/projio/bin/python3 -m projio.mcp.server` with `PROJIO_ROOT=/storage2/arash/projects/lit-studio` and `PROJIO_MCP_TOOLS=rag`. It kept 3 of 195 tools, and `corpus_list` and `rag_query` returned results.

## Request

1. When merging, treat any existing entry whose args are `-m projio.mcp.server` as projio's own, and set its `command` to the current interpreter (or the one passed with `python_bin`). Keep its `env` (`PROJIO_ROOT`, `PROJIO_MCP_TOOLS`) unchanged. Show the change in the preview.
2. Do the same for a `worklog` entry that runs `-m worklog.mcp_server` from conda when `worklog-mcp` is on PATH.
3. Optionally, a warning when any entry's `command` points into a conda env, as a nudge during the move.
4. projio decides whether the projio.mk conda defaults need the same treatment (pixi/uv), separately.

## How lit-studio will use it

lit-studio's gamma2 `.mcp.json` and pixecog's both have a `sirocampus` entry. pixecog adds a `lit-studio` entry (read-only, `PROJIO_MCP_TOOLS=rag`, R46). With this, regenerating moves all of them to the uv projio in one step, instead of hand-editing each file.

## Resolution (2026-11-11, projio-core · mcp-config)

Done in `src/projio/mcp/config_gen.py`. When `projio mcp-config` (and the `.vscode/mcp.json` writer) merges into an existing file:

1. Any other entry that runs `-m projio.mcp.server` gets the current interpreter (`runtime.projio_python`, else the Python running projio). `args` and `env` (`PROJIO_ROOT`, `PROJIO_MCP_TOOLS`) are kept.
2. Any entry that runs `-m worklog.mcp_server` gets the generated worklog command (`worklog-mcp` when it is on PATH, `args: []`). `env` is kept.
3. The preview and the write both list `[add]` / `[update] <name>: <old> -> <new>` lines and a `[warn]` for every entry whose command still runs from a conda env.

Entries that run anything else are left untouched. `projio init` on a project with an existing `.mcp.json` prints a hint naming the stale projio entries. Tests: `tests/test_mcp_config_gen.py`.

Item 4 (projio.mk conda defaults): the codegen already writes bare `projio`/`notio` and the uv env's mkdocs when a project sets no conda envs. The conda lines in pixecog's and sirocampus's projio.mk come from their own `code.conda_prefix` / `code.envs` config. See issue 20261028-010346-194501.

Preview on 2026-11-11: lit-studio's `sirocampus` and `worklog` entries move from `envs/rag` to the uv runtime. pixecog's `.mcp.json` was already on uv (rewritten 2026-11-08), so nothing changes there.
