## Task

Produce the **layout / spec** (not prose, not full content) for the handbook
and the September 2026 workshop, grounded in the tool-use survey produced by
the prior queued task.

This is a **structural pass**: chapter lists, section skeletons, exercise
specs, mapping tables. No paragraphs of finished writing. The goal is for
Arash to wake up to a concrete scaffold he can edit, approve, or redirect —
not a finished draft he has to undo.

## Inputs

- Tool-use survey: `docs/log/result/result-arash-20260508-tool-use-survey.md`

## What "layout / spec" means here

For each artifact below, produce the **structure and contracts** —
what goes where, what each piece must contain, what it cross-links to.
Stop at one-line-per-section depth; do **not** write chapter prose,
exercise solutions, or finished slide content.

### 1. Handbook layout spec

Write to: `docs/handbook/_outline.md` (create the directory if absent).

Contents:
- Full chapter list (refining the 7-chapter sketch in the idea note),
  one line per chapter
- Per-chapter sub-section list, one line each
- Per-chapter: which Deep Research paradigm(s) it anchors, which projio
  subsystem(s) it covers, which study-project examples (from the survey)
  it draws on, whether it has a planned marimo-WASM explorable
- Cross-link policy: how handbook chapters reference workshop sessions
  and vice versa
- Asset conventions: where figures live (`figio` vs static), where
  explorables live, naming pattern

### 2. Workshop syllabus spec

Write to: `docs/log/result/result-arash-20260508-workshop-syllabus-spec.md`
(the workshop workspace itself is not yet provisioned — the spec lives in
projio for now and migrates to `teaching/agentic-workshop/2026-09/syllabus.qmd`
when that workspace is created — see task
`task-arash-20260507-221947-582556.md`).

Contents:
- Per-day, per-session breakdown (4 days × 2 sessions/day, plus day-4
  presentations)
- Per-session: learning outcome (single sentence), prerequisite knowledge,
  hands-on artifact the participant produces, datasets used, the
  handbook chapter(s) it pairs with
- Pre-workshop setup checklist skeleton (one bullet per item, no full
  instructions)
- Day-4 rubric skeleton (criteria list, no scoring weights yet)
- Backup-plan skeleton (one bullet per failure mode: no internet, agent
  rate-limited, BYO data weirdness, install fails)

### 3. Handbook ↔ workshop mapping table

Append to the handbook outline file: a single table mapping each handbook
chapter/section to the workshop session(s) it supports, and vice versa.
This is the artifact that prevents duplication and ensures the workshop
can author against the handbook.

### 4. Marimo-WASM explorable shortlist

Append to the handbook outline: a shortlist of candidate explorables (3-5)
beyond the chapter-1 task-graph one already specified in
`task-arash-20260507-222051-589638.md`. Each entry: chapter target,
one-sentence concept the explorable teaches, rough interaction (slider,
graph builder, parameter cell), build cost estimate (S/M/L).

## Hard rules

- **Spec only.** No chapter prose, no finished exercise instructions, no
  finished slide text. If the temptation to write content arises, stop
  and capture it as a TODO bullet under the relevant section.
- **Ground in the survey.** Every "example from project X" claim must
  trace to a specific entry in
  `docs/log/result/result-arash-20260508-tool-use-survey.md`. If a chapter
  has no surveyed example, mark it `[example: TBD]` rather than inventing
  one.
- **Don't provision the workshop workspace.** That's a separate task
  (`task-arash-20260507-221947-582556.md`) that Arash may dispatch to a
  different session. Reference its planned path but don't create it.
- **Don't move the Deep Research PDF.** Separate task
  (`task-arash-20260507-222003-098400.md`). Reference the planned
  destination path in the spec.
- **Don't draft chapter 1.** Separate task
  (`task-arash-20260507-222028-504938.md`). The outline you produce
  *informs* that task; it doesn't replace it.

## Acceptance

## Why this two-step structure

A spec written without the survey would be ungrounded — it would invent
examples that don't exist. A spec written with the survey is editable
scaffold that Arash can approve in one pass and dispatch chapter-drafting
tasks against. The survey's output is the contract for this task's input.
