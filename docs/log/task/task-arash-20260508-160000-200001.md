## What "stack-component axis" means

Survey each component as a **horizontal slice** across all five projects,
not a per-project deep dive. For each component, the question is:
*"How does this stack component show up in projio's project-aware system,
and how does its adoption vary across study projects?"*

The seven stack components (introduce in this order in the handbook /
workshop):

1. **BIDS** — neuroscience data layout standard
2. **DataLad** — versioning data + code, subdatasets, siblings, annex
3. **Snakemake** — pipeline orchestration (snakebids + pipeio adapters)
4. **Marimo** — reactive notebooks, both for analyses *and* for explorables
5. **Quarto and/or MkDocs** — publication framework (multi-output Quarto for
   workshop; mkdocs-material for handbook)
6. **projio** — the layer that knows about the stack and helps coordinate
   it (subsystems: codio, biblio, notio, figio, pipeio, indexio,
   manuscript)
7. **Agentic workflows on top** — Claude Code settings, MCP servers,
   project-local + ecosystem skills, captures → tasks → queue dispatch

## Per-component survey schema

For each component, document:

1. **What the component does** in this stack — one-paragraph operational
   definition, framed for a workshop audience.
2. **How projio is aware of it** — which projio subsystem(s), config keys,
   conventions, MCP tools touch this component (e.g. for BIDS: `pipeio.adapters.bids.BidsPaths`,
   `manifest.yml` contract; for DataLad: `mcp__projio__datalad_*` tools,
   sibling helpers).
3. **Adoption table across the five projects** —

   | Project | Adopted? | How / signature artifact | Variation worth teaching |
   |---|---|---|---|

4. **Convergent patterns** — what's universal (e.g. all study projects
   use BIDS `raw/` + `derivatives/<flow>/`).
5. **Divergent patterns** — what differs (e.g. pixi vs conda; MkDocs vs
   Sphinx; snakebids-direct vs pipeio adapter).
6. **One canonical teaching artifact** — a single concrete file/path/flow
   to dissect for that component. Prefer paths that exist in *one* project
   and aren't workshop-domain-specific.
7. **Honest gap** — where the component is under-adopted, drift exists,
   or the convention is still in flux.

## projio-introduction grading (specific to component 6)

The handbook introduces projio **gradually**: start by using BIDS +
DataLad + Snakemake + Marimo + Quarto without it (workshop day 1 + early
day 2), then bring projio in as the layer that *knows* about those
conventions. For component 6, additionally produce a **graded
introduction sequence**:

| Stage | What's added | Workshop session that introduces it | Stack-awareness payoff |
|---|---|---|---|

The stages should be ordered to motivate each subsystem from the pain it
solves in the prior stage (e.g. "now you have 12 BIDS derivatives dirs and
no record of which Snakemake config produced each — that's what projio's
notio + agent-activity solves").

## Agentic-on-top schema (specific to component 7)

For the agentic component, additionally inventory across projects:

- `.claude/settings.json` permission shape (which MCP tools pre-approved,
  which Bash commands, which Read paths; tool wildcards vs explicit names)
- `.mcp.json` server set (projio + worklog + sirocampus baseline; gecog's
  fourth `cogpy` server is the standout)
- Skills (project-local under `.projio/skills/` vs ecosystem; which are
  invoked vs dormant)
- Captures → tasks pattern (worklog `worklog_note(auto_dispatch=True)`,
  `promote_to_task`, `schedule_queue` with `after=` chains — this very
  session's pattern is itself a teaching artifact)
- Hooks (any custom `.claude/settings.json` hooks for events like Stop /
  PreToolUse)
- Routing (gamma/gpu host selection, model selection — opus for synthesis,
  sonnet for execution, haiku for triage)
