## Task

Survey **how the projio toolchain is actually used** across projio itself and the
four active research-kind projects in the worklog registry: `cogpy`, `pixecog`,
`gecog`, `msol`. The output of this survey is the empirical input to the
handbook-and-workshop layout/spec task that runs after this one.

This is **read-only research**. Do not modify any of the surveyed projects.
Write the survey output to projio only.

## Why this is the right first step

The handbook (chapter list, examples) and workshop (per-day exercises,
datasets, hands-on flow) need to be grounded in **real, recurring patterns**
from Arash's own work — not from idealized descriptions of projio's surface.
Inspirations (Mineault, Wickham, Ciechanowski) all draw their authority from
working examples. The survey produces those examples and exposes the gaps so
the spec task can scope honestly.

See companion idea note for the full initiative:
`docs/log/idea/idea-arash-20260507-221835-382557.md`.

## Scope — what to survey

For each of the five projects (`projio`, `cogpy`, `pixecog`, `gecog`, `msol`):

1. **Tool inventory** — which projio MCP tools, skills, and CLI surfaces are
   actually invoked? Pull from:
   - `.claude/settings.json` permissions (allowed MCP tools) — narrows the
     surface area the project agent uses
   - `.projio/config.yml` and `.mcp.json` — what's wired up
   - notio `agent-activity.md` and recent `commit/` log entries — what tools
     have actually fired
   - skill_read inventory (which skills are present + invoked)

2. **Subsystem footprint** — for each of the six subsystems (indexio, biblio,
   notio, codio, pipeio, figio): is it active, dormant, or absent? What's the
   signature artifact in the repo (e.g. `bib/srcbib/*.bib` for biblio,
   `code/pipelines/*/` for pipeio)?

3. **Conventions in use** — BIDS layout? DataLad sibling configuration?
   Snakemake workflow style? Notebook backend (jupytext vs marimo)? Tier
   layout (`code/lib/`, `code/utils/`, `code/pipelines/`)?

4. **Concrete teaching-grade examples** — pick 1-3 things in each project
   that would make a *good workshop exercise or handbook example* (a real
   pipeline rule worth dissecting, a non-trivial figio FigureSpec, a real
   codio reuse decision, a manuscript section flow). These are the
   handhold artifacts the workshop will build around.

5. **Friction / gaps** — where does the agent currently struggle, where do
   tools collide, what's still manual that the handbook should call out as
   "honest current limit" (per the Deep Research frame's fragility warning).

## Method

- Use `mcp__worklog__worklog_project_context(project_id)` to get each
  project's snapshot before diving in (avoids re-exploring directory
  structure manually).
- Use `mcp__worklog__worklog_read_file` for cross-project reads — do not cd
  into other projects.
- Use `mcp__projio__codio_list`, `mcp__projio__pipeio_flow_list`,
  `mcp__projio__pipeio_mod_list`, `mcp__projio__figio_figure_list`,
  `mcp__projio__manuscript_list`, `mcp__projio__note_list` to inventory
  artifacts inside projio itself.
- For other projects, fall back to `worklog_read_file` of their `.projio/`
  configs and key `code/`, `bib/`, `docs/log/` directories.
- Skip MSOL deeper dives if the project is too early-stage to yield useful
  signal — note that in the report.

## Output

Write one survey document to:

`docs/log/result/result-arash-20260508-tool-use-survey.md`

Structure:

1. **Per-project sections** (5 sections: projio, cogpy, pixecog, gecog,
   msol) — each with: tool inventory, subsystem footprint, conventions,
   teaching-grade examples, friction notes.
2. **Cross-project synthesis** — patterns that recur, divergences worth
   highlighting in the workshop (e.g. "all three ECoG projects share BIDS
   layout but differ in pipeline style").
3. **Recommended teaching artifacts** — a shortlist (5-10) of the strongest
   concrete examples to build workshop exercises around, ordered by
   leverage. Each entry: source project, what the example demonstrates,
   which handbook chapter / workshop day it suits.
4. **Honest gaps** — what's still manual / fragile / inconsistent across
   projects that the handbook should acknowledge rather than paper over.
