# pipeio_nb_report MCP tool + /report skill

## Summary

- New `pipeio_nb_report(flow, name)` MCP tool extracts figures, markdown, and text outputs from executed notebooks into structured payloads for report writing
- New `/report` skill orchestrates extraction + agent-written curated report at `{flow}/docs/reports/{name}.md`
- Reports are git-tracked source files (not build artifacts), published via existing `docs_collect`

## Details

- **Backend-aware extraction**: dispatches to `_nb_report_percent` (nbconvert on `.ipynb`) or `_nb_report_marimo` (`marimo export md`) based on notebook format config or auto-detection
- **HTML widget detection**: identifies holoviews, bokeh, plotly, ipywidgets outputs that render as interactive HTML but can't be extracted as static images; returns `html_outputs` list + `html_outputs_hint` with remediation guidance (hv.save, export_png, write_image)
- **Cell tagging**: `tags_only=True` filters to cells marked with `# REPORT:` (percent-format only)
- **Figure extraction**: saves PNGs to `{flow}/docs/reports/{name}/`, idempotent (skip if exists unless `overwrite=True`)
- **Skill workflow**: extract -> check existing report -> write curated markdown with figures, captions, metrics, interpretation -> optionally capture result note
- Tool count: 53 -> 55 (with `pipeio_nb_validate` and `pipeio_nb_watch` from concurrent marimo backend work)

## Motivation

- Explore notebooks accumulate 30+ cells but key findings are buried in 5-6 plots -- extracting results is slow
- Motivated by pixecog TTL characterization notebook; cross-subject and badlabel audit notebooks confirmed the holoviews gap
- Flow-local `docs/reports/` convention keeps reports next to the code they describe, vs project-wide `docs/deliverables/` which aggregates across flows
